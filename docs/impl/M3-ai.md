# M3 AI 확장

설계도 18장: "게이트웨이 인증 전환, v2 계약, 한도 · 체험 · KST, 결과 카드(다중), 묶음 지출". 담당: 백엔드 + 프론트.

**완료 기준(설계도 18):** **14.6 수락 시험 전부 통과, 차감 규칙 시험 통과.**

선행: M2(로그인 토큰 · `profiles` · `create_profile`), M1-03(시간 규칙과 시험 벡터 JSON), 결정 D-10 · D-13(수입 문장). OpenAI 키는 서버 비밀 저장소에만 둔다(M0-04).

## 현재 서버 상태 (`server/`, 설계도 14.1)

Node 24, 외부 의존성 없음. 파일럿 토큰(`vlm_`) 인증, OpenAI Responses + 엄격한 JSON 스키마(`store: false`), `GET /healthz · GET /v1/session · POST /v1/interpret`. 응답은 **단일 지출 제안만**. 한도: 사용자당 분당 6 · 하루 30 · 동시 1, 전체 하루 500, 일일 기준 **UTC**. 맨 "7시"는 모델에 맡기지 않고 질문으로 처리(`guardAmbiguousTime`).
**유지할 강점:** 호출 전 원자적 예약, `requestId` 멱등 재생, 7일 지문 보관, 로그에 본문 미기록, 서버 · 클라이언트 양쪽 검증. 테스트는 `server/test/gateway.test.mjs`.

## 서버 단위 (B)

### B3-01 인증 전환 (설계도 14.3)
- 파일럿 토큰 → **Supabase 액세스 토큰(JWT) 검증**. 사용자 id는 JWT의 `sub`. 클라이언트가 보낸 사용자 id 같은 값은 쓰지 않는다(16.2).
- 활성 기기 검사(`DEVICE_REPLACED`)도 적용한다(M2 B2-02의 규칙).
- 배치 위치(14.3): (A) 현재 Node 서버 유지 + 별도 호스팅, (B) Supabase Edge Function으로 이식 — **백엔드 담당이 결정**하고 결정 사유를 `docs/impl/m3-decisions.md`에 기록. (A)는 검증된 코드를 그대로 쓰고, (B)는 구성 요소가 줄어든다. 어느 쪽이든 이 단위의 완료 기준은 같다.

### B3-02 한도 · 체험 · 사용량 (설계도 9.1, 13.6, 4.7)
- 테이블(13.6): `entitlements`(M5에서 채워짐, 지금은 기본 `FREE`), `usage_counters(bucket: 'month:<주기 시작>' | 'day:<KST 날짜>')`, `trials(ai_left 0~3, share_left 0~1)`, trials 행은 **M2 `create_profile` 트랜잭션에서 함께 만들도록 확장**한다(재가입이면 새 계정이므로 다시 지급). **M2에서 이미 만들어진 계정에는 `ai_left = 3`, `share_left = 1`로 백필**하는 마이그레이션을 같이 둔다.
- 원자적 차감 함수: `insert … on conflict (user_id, bucket) do update set ai_used = ai_used + 1 where ai_used < 한도 returning ai_used`. **일 bucket · 월 bucket(구독자) 또는 `trials.ai_left`(체험)를 같은 트랜잭션에서** 차감, 하나라도 실패하면 전체 롤백. 결과가 없으면 한도 초과.
- 흐름: 호출 전 **예약** → 성공(PARSED · 질문 응답 포함)이면 확정, **서버 오류 · 시간 초과 · 모델 응답의 서버 검증 실패 · UNSUPPORTED면 사용자 횟수 환원**(비용 예산 카운터에는 남김). 환원은 `requestId`당 1회만.
- **하루 한도는 KST 자정 초기화**(현재 UTC → 변경), 월 한도는 결제 주기 시작(`period_start`)마다. 구독 중에는 체험 횟수를 쓰지 않고 보존, 만료 후 남아 있으면 다시 사용(9.1).
- 후속 호출(질문 답변)은 차감하지 않는다: 원래 요청 후 **10분 이내, 원래 요청당 최대 2회**(4.7). 넘으면 새 요청으로 1회 차감.
- 비용 예산(전체 하루 · 시도당 예약)은 구독자 수에 맞춰 상향 가능한 **운영 설정값**으로 뺀다.
- `get_entitlement`(13.7)의 **FREE · 체험 · 사용량 부분을 여기서 만든다**: `{ plan, 한도, 사용량, 체험 남은 수, 주기 종료일 }`. M5 B5-02는 이 함수에 구독 정보를 붙여 확장한다(앱 F3-05의 사용량 표시가 M3에서 서버에 연결되도록).
- 완료 기준: 한도 경계(150번째 · 151번째, 20번째 · 21번째, KST 자정 직전 · 직후), 동시 요청 경쟁, 환원 1회 제한 시험.

### B3-03 v2 계약 `POST /v2/interpret` (설계도 14.4)
요청: `{ requestId, sourceInput(≤1000자), inputMethod: TEXT|VOICE, now, timeZone, followUp: null | { previousRequestId, actionId, question, answer } }`.
응답: `{ status: OK|UNSUPPORTED, message, actions[], usage{ aiLeftToday, aiLeftPeriod, trialLeft } }`. 액션: `CREATE_TRANSACTION`, `CREATE_EVENT`, `CREATE_TASK`, `CREATE_REMINDER`, `SEND_EVENT`, `SEND_EXPENSE` — **최대 10개**, 각각 `id`, `type`, `state: READY | NEEDS_CLARIFICATION`, `question`, `payload`, `dependsOn`.
- 모델에 보내는 정보는 **문장 · 기준 시각 · 시간대 · 지침 · 스키마뿐**. 사용자 id · 친구 목록 · 기록 · 음성은 보내지 않는다(14.4).
- **시간:** 모델은 `hour`, `minute`, `meridiemExplicit`, 상대 날짜만 추출하고, **최종 시각은 서버 코드 한 곳이 계산**한다(`autoMeridiem` 표시값 포함). 모델 추측에 맡기지 않는다. 서버의 시간 규칙은 앱 TS 모듈(M1-03)과 **별도 구현**이며, 두 구현의 동등성은 **공용 시험 벡터 `docs/impl/time-vectors.json`(M1-03에서 확정)을 양쪽이 같은 시험으로 통과**하는 것으로 보장한다.
- `followUp`: 앱이 `sourceInput`에 **원문을 다시 담아** 보내는 방식을 권장(14.4). 서버가 원문을 보관하지 않아도 동작.
- 서버가 액션 봉투(`actionId`, `type`, `dependsOn`)를 소유하고 모델 출력은 신뢰하지 않는다(기존 `toProposal` 방식 유지). `UNSUPPORTED`(부정 · 계획 · 질문 · 수입 문장 — D-13 권장안 기준)는 기록 없음.
- 모델 지침(14.5): 실제로 쓴 지출만 · 묶음 지출 규칙(4.5) · 시간은 숫자와 단서만 · "이걸 OO에게 줘/보내줘/넣어줘"는 보내기 액션, "나도/내 캘린더에도/같이 넣어줘"는 `includeInMyCalendar: true` · 장소는 `location`으로 분리 · 카테고리는 정해진 목록(식비 · 교통 · 생활 · 쇼핑 · 의료 · 문화 · 기타 — `server/src/contracts.mjs`에서 확인한 값이며 설계도 14.5는 "앱의 카테고리 목록과 동일"이라고만 함, 앱 목록과 항상 동기화)만 · 확신이 없으면 `NEEDS_CLARIFICATION`.
- 완료 기준: v1 엔드포인트와의 호환 정책(앱이 v2로 바뀌면 v1은 제거 또는 개발자용으로만) 기록.

### B3-05 AI 동의 기록 (설계도 16.1)
- `profiles.ai_consent_at timestamptz NULL` 컬럼 추가(설계도 13.1에는 없는 **확장 컬럼** — 마이그레이션에 사유를 주석으로 적는다). 함수 `record_ai_consent`: 활성 기기 검사 후 현재 시각을 기록(이미 있으면 유지), `get_entitlement` 응답에 `aiConsent: boolean` 포함. 동의 철회는 1차 범위 밖(확인 필요).
- 완료 기준: 동의 기록 · 재설치 후 유지 · 다른 사용자 동의 값 읽기 · 쓰기 거부(RLS).

### B3-04 수락 시험 자동화 (설계도 14.6)
아래 입력(기준 시각 KST)을 **자동 시험**으로 만든다. 제공자(OpenAI) 호출은 모의 응답으로 서버 로직(시간 계산 · 묶음 규칙 검증)을, 실제 모델 호출은 별도 "라이브 시험"(수동 실행, 비용 발생)으로 둔다.

| 입력 | 기대 결과 |
| --- | --- |

| 친구랑 7시 약속 (20:00) | 일정 NEEDS_CLARIFICATION "내일로 할까요?" |

- 모델 교체(`OPENAI_MODEL`, 예: gpt-4.1-nano · GPT-5 mini) 전에는 이 시험을 다시 통과해야 한다(14.2).
- 완료 기준: 위 표 전부 + 차감/환원 시험이 자동으로 통과.

## 앱 단위 (F)

### F3-01 AI 클라이언트 v2 · 인증 (설계도 12.2)
- `adapters/ai/http-capture-ai-interpreter.ts`를 v2 계약으로 바꾼다. Supabase 로그인 토큰으로 자동 인증, `requestId` 멱등. 응답을 **앱 검증기(`application/validator`)로 다시 통과시켜야 저장**한다(4.7). 시간은 앱이 **재계산하지 않고 구조만 검사**한다: UTC ISO 형식, 지난 시각 여부, `autoMeridiem` 표시값의 유무(서버가 최종 시각을 계산한다는 AGENTS.md 원칙 유지).
- 기존 **AI 연결 설정 화면(`features/settings/ai-connection-screen.tsx`, `app/ai-settings.tsx`)은 개발자 전용으로 숨긴다**(일반 사용자에게 서버 주소 · 토큰 입력 노출 금지). 개발 빌드에서만 보이는 플래그로 감싼다.
- 시간 초과 · 서버 오류는 차감 없음 문구와 함께 처리(F3-04).

### F3-02 입력 라우터 완성 (설계도 4.2, 시안 `submitCapture`)
순서: 로컬 파서 가능 → 로컬 저장(AI 없음). 아니면 AI 필요 → 
- **게스트:** "로그인하면 AI 체험 3회를 쓸 수 있어요" + [로그인] / [직접 입력].
- **무료 · 체험 남음:** "AI 체험 N회 남음, 사용할까요?" → [사용하기] / [직접 입력].
- **무료 · 체험 없음:** "AI가 필요해요" + [구독 보기] / [직접 입력(문장을 제목 · 메모 칸에 채움)]. **[구독 보기] · [요금제 보기]의 이동 대상(B1)은 M5에서 생기므로, M5 전에는 이 버튼을 표시하지 않고 문구와 [직접 입력]만 보인다**(M1-10의 "없는 화면으로 가는 버튼은 숨김" 원칙과 같다).
- **구독 · 한도 남음:** 바로 호출. 한도 초과 시 "이번 달 / 오늘 한도를 다 썼어요" + 다시 채워지는 시점 + [직접 입력](기본 플랜은 [요금제 보기]).
- **오프라인:** AI를 부르지 않고 "처리 대기 초안"으로 보관 → 연결 후 사용자가 직접 [다시 처리](자동 실행 금지, M1-11).
- **첫 AI 사용 전 동의(설계도 16.1):** 체험 사용 확인 · 한도 확인을 통과한 뒤, 첫 호출 직전에 "입력한 문장은 AI가 해석하도록 OpenAI(미국)로 전송돼요. 이름 · 친구 목록 · 기록은 보내지 않고, 음성 녹음은 저장하지 않아요. 동의하지 않아도 직접 입력은 계속 쓸 수 있어요." [동의하고 계속] / [직접 입력]. 동의 여부는 서버에 기록(B3-05 `record_ai_consent`, `profiles.ai_consent_at`)해 재설치 후에도 유지(1회). 동의 전에는 AI를 부르지 않으며 차감도 없다. 시안: `runAi` 동의 래퍼 · 디자인 바 "AI 동의".
  - **문구와 처리 위탁 · 국외 이전 고지의 법적 적합성은 확인 필요**(16.1). 법률 검토 결과에 따라 문구를 바꾼다.
- 수입 문장은 D-13 권장안에 따라 AI도 기록하지 않는다(안내 후 [직접 입력]). **D-13 확정 전까지 안내 문구는 임시**이며, 확정이 "수입도 기록"이면 이 줄과 F3-04의 해당 문구를 함께 바꾼다.
- 시험: 위 6가지 분기, 오프라인 초안, 동의 전 미호출.

### F3-03 다중 액션 결과 카드 (H2, 설계도 4.3, 14.4)
- 응답의 액션마다 카드 하나. 상태 3종: **저장됨 / 질문 대기 / 실패**. 각 카드 [되돌리기] · [수정].
- **독립 액션은 다른 액션이 질문 대기여도 먼저 저장.** `dependsOn`이 있는 액션(예: "1시간 전 알림")은 대상 일정이 확정될 때까지 대기 → 일정이 확정되면 자동으로 이어서 처리.
- 자동 오전/오후 판단이 있으면 카드에 "오후 7시로 저장했어요" + [수정].
- **보내기 액션(SEND_*)은 저장하지 않고 보내기 확인 화면을 연다**(M4의 S1과 연결). M3 시점에는 친구 기능이 없으므로, 응답에 보내기 액션이 섞여 있으면 **그 액션만** "보내기는 친구 기능이 열린 뒤에 쓸 수 있어요"라는 실패 카드로 표시하고 나머지 액션은 정상 저장한다(성공처럼 보이지 않게). 이 카드의 자리는 M4-F4-04에서 보내기 확인 화면으로 바뀐다.
- 질문 입력: 질문 카드에 답을 입력(또는 [오전] [오후] [내일로] 같은 선택지) → 후속 호출(F3-04).
- 시험: 설계도 4.3의 예시 두 건("밥 7000원짜리 먹었고 오늘 친구랑 오후7시 약속있다", "점심 8천원 썼고 내일 민수 만나. 한 시간 전에 알려줘"), 부분 성공 표시.

### F3-04 후속 질문 · 차감 · 오류 처리 (설계도 4.7 · 15)
- 후속 호출은 **원래 요청 후 10분 이내 · 원래 요청당 2회까지 차감 없음**, 넘으면 새 요청(1회 차감). 시안 `followUpCharge`, `FOLLOWUP_WINDOW_MS`.
- 서버 오류 · 시간 초과: "잠시 후 다시 시도해 주세요" + [다시 시도] + [직접 입력], 차감 없음 문구. [다시 시도]가 성공하면 오류 카드는 사라진다.
- 해석 불가(UNSUPPORTED): "안 쓴 돈 · 받은 돈(수입) · 계획이나 질문은 기록하지 않아요. 횟수는 차감되지 않아요" + [직접 입력]. ("받은 돈(수입)" 부분은 D-13 확정 후 확정 문구.)
- **서버 검증을 통과했지만 앱 검증에서 걸린 경우:** 저장하지 않고 **차감은 유지**(4.7), 오류 추적 id를 기록(로그에는 문장 본문을 남기지 않는다), [다시 시도] 없음.
- 알림 예약 실패(M1-08, `lastError`가 있는 `REQUESTED` 상태)는 일정 카드에 "알림 예약 실패" + [알림 다시 시도].
- **사용자가 저장 결과를 되돌려도 차감은 유지**(4.7) — 되돌리기 후 횟수가 환원되지 않아야 한다.
- 시험: 위 4가지 + 10분 경계 · 3번째 후속(차감) + 되돌리기 후 차감 유지.

### F3-05 사용량 표시 · H3 안내 · 구독 구역 자리 (설계도 11.2 H1 · H3, 10.1)
- 홈 H1: AI 사용량(구독자 `이번 달 N/150 · 오늘 N/20`, 무료 `체험 N/3`), 서버 `get_entitlement` 값을 **표시용으로만 캐시**하고, 허용 여부는 항상 서버가 판단(12.5). 요금제 · 사용량 문구에 "무제한"을 쓰지 않는다.
- 설정 > 구독 구역의 현재 플랜 · 사용량 · 체험 남은 횟수 · [플랜 보기](결제는 M5).
- 시험: 서버 값이 바뀌면 표시가 바뀐다(캐시 갱신 시점: 앱 시작 · 포그라운드 전환 · 호출 직후 응답의 `usage`).

### F3-06 묶음 지출 저장 (설계도 4.5, 12.3)
- **로컬 파서는 "총 · 합쳐서 · 다 해서 · 전부 해서 · 모두"가 들어간 묶음 문장을 처리하지 않고 AI로 넘긴다**(시안 `localParse` 보정). 로컬 파서는 단일 항목 · 단일 금액만.
- **금액이 없는 묶음 문장**("아이스크림이랑 생수랑 밥 먹었어")은 AI 호출 결과 `NEEDS_CLARIFICATION` "총 얼마였어요?"로 질문 카드를 만들고, 입력한 금액으로 후속 호출 · 저장한다(차감 없음).
- **메모에는 항목 이름과 개별 금액을 남긴다**(예: "아이스크림 2,000원, 생수, 밥"). 동사 · 조사는 메모에서 뺀다.
- 서버가 정한 결과(총액이 있으면 1건 + 메모 "아이스크림, 생수, 밥" + `bundle_items`, 모든 금액 + 총액 없음이면 건별 분리)를 그대로 저장. 합 불일치 · 금액 없음은 질문 카드. 카테고리는 같으면 그것, 섞이면 "기타".
- 앱은 서버 응답을 **같은 규칙으로 다시 검증**: 총액이 있는데 개별 금액의 합과 다르면 저장하지 않고 질문, 총액이 있으면 항상 1건, 총액이 없고 모든 항목에 금액이 있을 때만 건별 분리.
