# M4 친구 · 공유

설계도 18장: "링크 · QR · 닉네임, 수신 설정, 보내기 · 받기 · 수정 · 취소 · 삭제 기록, 푸시, 서버 대체 알림, 공개 일정 · 친구 일정 보기, 프로필 사진, 차단 · 신고, 초기화 (a)(b), 음성으로 보내기". 담당: 백엔드 + 프론트. 가장 큰 단계이므로 서버 · 앱을 **작은 단위로 번갈아** 진행한다.

**완료 기준(설계도 18):** **두 실기기(iOS · Android)로 6장 전 흐름 시연**, **보낸 사람에게 수락 여부가 노출되지 않음을 API로 확인.**

선행: M2(계정 · 활성 기기 · 백업 · 프로필 설정 동기화), M3(`entitlements` 뼈대), 결정 D-2 · D-4 · D-5 · D-7 · D-14 · D-15 · D-17 · D-18. 도메인과 앱 연결 파일(M0-03).

**M5 전의 구독자 흉내(개발용 플래그):** 서버 코드에 환경변수 분기를 넣지 않고, **개발 DB의 시험 계정 `entitlements` 행을 `PLUS · ACTIVE`로 직접 넣는 방식**으로만 한다. 그러면 M5에서 서버 검사가 `entitlements.status`를 읽게 바뀌어도 같은 시험 계정이 그대로 동작하고, 출시 빌드에 남을 플래그 코드가 없다(M5 B5-04 완료 기준에 "플래그 코드 없음" 확인 포함).

**작업 단위 크기:** 아래 B4-02 · F4-04 · F4-07은 한 번에 하나씩 맡기기엔 크므로 각 단위 안의 `(a) (b) …` 하위 단위를 **하나씩 따로 요청**한다.

## 핵심 불변 규칙 (구현 중 계속 확인)

1. **보낸 사람은 `전달 대기 중 / 전달 완료 / 만료됨 / 취소됨`만 본다.** 수락 · 확인만 · 삭제 · 알림 꺼짐 여부는 어떤 API 응답에도 없다(6.1, 6.4, 13.3, 13.8).
2. 보내기 · 받기 · 취소는 **서버가 최종 판정**한다(`routed_mode`는 서버가 전송 시점에 기록, 앱은 그대로 따른다).
3. 받는 사람이 지운 항목은 **되살아나지 않는다**(삭제 기록 `recipient_deleted_at`).
4. 서버는 받는 사람 폰의 로컬 DB에 직접 쓸 수 없다. 받은 항목이 실제로 들어가는 것은 받는 사람 앱이 `sync`를 실행했을 때다(6.7). 그래서 **서버 대체 알림**이 필요하다.
5. 차단 사실을 드러내지 않는다: 차단된 상대에게 보내면 오류는 `NOT_AVAILABLE`("보낼 수 없는 상대예요")로 통일(13.8).

## 서버 단위 (B)

### B4-01 친구 테이블 · 초대 · 요청 · 차단 · 신고 (설계도 13.2)
- `friend_links`(방향별 1행), `invite_links`(토큰은 128비트 이상 무작위, **서버에는 해시만**), `friend_requests`(`PENDING` 부분 유니크), `blocks`, `reports`.
- 함수(보안 정의자):
  - `create_invite`: `{ url: https://<도메인>/i/<토큰>, expiresAt(+5분) }`, 이전 미사용 링크 무효화, 분당 5회 제한.
  - `redeem_invite`: **한 트랜잭션** — 토큰 해시로 행 잠금(`for update`) → 만료 · 사용 여부 · 본인 · 차단 · 이미 친구 · 30명 확인 → `used_by` 기록 → `friend_links` 두 행 생성(이미 `DISCONNECTED` 행이 있으면 `ACTIVE`로 복귀하고 별명 · 수신 모드 유지) → 초대자에게 푸시(**푸시 발송 모듈은 B4-04에서 만든다. 이 단위에서는 `notify(userId, type, payload)` 인터페이스 호출까지만 하고, 시험은 가짜 구현으로 한다**). 결과 코드: `CONNECTED | EXPIRED | USED | ALREADY_FRIENDS | SELF | BLOCKED | LIMIT`. 동시에 두 명이 열어도 한 명만 성공.
  - `search_nickname`: **정확히 일치 + `searchable` + 차단 관계 아님**일 때만 1명(닉네임 · 이니셜만, 사진 없음). 사용자당 분당 10회 제한.
  - `send_friend_request` / `respond_friend_request`(A→B와 B→A가 동시에 대기 중이면 자동 연결).
  - `update_friend_settings`: `alias`(1~20자, 본인만 읽음), 수신 모드 2종(일정 · 지출: ASK / ALWAYS_ADD / ALWAYS_VIEW / NOT_ALLOWED), 알림 2종, `hidden_all`, `in_audience`, `include_expense_in_total`.
  - `disconnect_friend`, `block_user`(양방향 `DISCONNECTED` + 대기 전달 취소), `unblock_user`, `report_user`(사유: AVATAR · NICKNAME · SPAM · OTHER + 설명).
- **친구 상한 30명:** `ACTIVE` 연결 + 내가 보낸 `PENDING` 요청만 센다(`DISCONNECTED` 제외). 동시 연결로 31명이 되지 않도록 두 사용자의 `profiles` 행을 id 순서로 `for update` 잠근 뒤 검사.
- `can_send_to(friend_id)`: 상대가 나에게서 받기를 허용했는지 `{ event, expense }`만 돌려준다(상대의 별명 · 수신 모드 · 공개 설정은 노출 금지).
- 완료 기준: 링크 동시 사용 경쟁 시험(한 명만 성공), 만료 · 재사용 · 본인 · 차단 · 30명 시험, 닉네임 검색 제한 시험, RLS 시험.

### B4-02 공유 항목 · 전달 · 보내기 (설계도 13.3 · 13.4 · 13.7, 6.6) — 하위 단위: (a) 테이블 · payload 검증 · 만료 계산 / (b) `send_item` 검사 순서와 50건 차감 / (c) `routed_mode` · 상태 뷰
- 테이블: `shared_items`(`client_request_id` 멱등, `starts_at`, `version`, `status`), `deliveries`(`state`, `routed_mode`, `expires_at`, `delivered_at`, `recipient_deleted_at`, `is_trial`), `always_add_counters`.
- **payload 검증(서버, 앱을 믿지 않음):** EVENT `{ title(≤100), timeKind: EXACT|FUZZY|ALL_DAY, startAt, fuzzyTime, date, endAt, timezone, location(≤100), reminderOffsets }`, EXPENSE `{ amount(1~1억 정수), currencyCode, category, memo(≤500), occurredAt, bundleItems }`. `reminderOffsets` 허용값은 정시(0) · 10분 · 30분 · 1시간 · 하루 전(음수, D-15)만. 시간 종류 FUZZY · ALL_DAY도 허용(D-4). **`timeKind ≠ EXACT`이면 `reminderOffsets`는 빈 배열만 허용**(D-3 — 종일 · 대략적 시간 일정은 알림이 없다).
- **`starts_at`은 항상 채운다:** EXACT = 시작 시각, ALL_DAY · FUZZY = 그날 23:59 KST. `expires_at` = EVENT면 `least(starts_at, created_at + 30일)`, EXPENSE면 `created_at + 30일`. 보낸 사람이 시각을 수정하면 같은 트랜잭션에서 `starts_at`과 PENDING 전달의 `expires_at`을 다시 계산.
- `send_item({ clientRequestId, kind, payload, recipientIds[] })` — **검사 순서(13.7)**: 인증 · 활성 기기 → 구독 또는 체험(체험이면 `kind = EVENT`, 수신자 1명) → 지난 일정 거부(`PAST_EVENT`) → 수신자별 관계 · 차단 · 받기 허용(`NOT_AVAILABLE`) → **유효한 수신자 수만큼 하루 50건 원자 차감**(`usage_counters.sends_used`, bucket `day:<KST 날짜>`; KST 자정 초기화, 남은 건수가 부족하면 전체 거부 `DAILY_LIMIT` + 응답에 남은 건수) → 수신자별 `routed_mode` 판정(항상 넣기 카운터 원자 증가) → 행 생성 → 푸시. **모두 한 트랜잭션.** 같은 `clientRequestId` 재요청은 같은 결과. 응답은 수신자별 `{ deliveryId | error }`(`NOT_ENTITLED`, `TRIAL_USED` 포함).
- **`routed_mode` 판정:** 받는 사람의 수신 모드를 읽어 기록(최종값). `ALWAYS_ADD`인데 그 보낸 사람이 오늘(KST) 그 받는 사람에게 `ALWAYS_ADD`로 판정된 건이 이미 20건이면 `ALWAYS_VIEW`로 기록하고 받는 사람에게 "OO님이 오늘 많은 일정을 보냈어요. 수신함에서 확인하세요" 알림을 하루 한 번. 카운터는 `insert … on conflict … do update set n = n + 1 returning n`으로 원자 증가하며 `ALWAYS_ADD`로 판정될 때만 센다.
- 전송 후 받는 사람이 그 친구를 "받지 않기"로 바꾸거나 차단하면 PENDING 전달은 `WITHDRAWN`.
- **보낸 사람용 상태는 내부 상태와 분리:** 직접 취소 → 취소됨, `DELIVERED` → 전달 완료(받은 사람이 나중에 지워도 그대로), `PENDING` → 전달 대기 중, 그 밖의 종료(만료 · 차단 · 받지 않기 전환 · 전달 전 삭제) → 만료됨. 보낸 사람은 `sent_delivery_status`(`id, item_id, recipient_id, state, delivered_at`만)로만 본다. `deliveries` RLS SELECT는 `recipient_id = auth.uid()`만.
- 완료 기준: **API로 보낸 사람 토큰이 `recipient_deleted_at`, `routed_mode`를 어떤 경로로도 읽지 못함**을 시험으로 증명, 하루 50건 경계(49 + 수신자 2명 = 거부), 항상 넣기 20건 경계, 체험(수신자 1명 · 일정만 · 평생 1회 · 거절되면 복구는 서버 판정 — **README 3.1 #4 확인 전 가정**), 멱등 재요청.

### B4-03 수정 · 취소 · 삭제 · sync · ack (설계도 6.5, 12.4, 13.7)
- `update_item` / `cancel_item`: **보낸 사람만, 구독이 만료돼도 허용**. `version + 1`. 삭제 기록이 없고 차단 관계가 아니며 전달이 종료되지 않은 수신자에게만 반영 · 푸시. 연결 해제된 수신자에게는 반영(연결 해제는 항목 유지, 3.7). 취소: 수신자 폰의 일정은 `CANCELLED`(취소선 + "보낸 사람이 취소했어요"), 지출은 수신자 폰에서 삭제(합계 제외), 전달 전이면 전달하지 않음.
- `delete_received` / `delete_all_from_sender`: `recipient_deleted_at` 기록(전달 대기면 전달도 중지). 이후 수정 · 취소는 그 사람에게 내려가지 않는다.
- `sync(cursor)` → `{ deliveries, friends, sentStatus, account{ deviceReplaced?, plan }, nextCursor }`, `ack_deliveries([{ deliveryId, version }])` → `DELIVERED` 기록.
- **동기화 커서(`change_log`):** 시각이 아니라 `bigserial seq`. 모든 변경은 관련 사용자별로 **같은 트랜잭션에서** 한 행씩 기록(`DELIVERY_NEW | DELIVERY_UPDATED | DELIVERY_CANCELLED | FRIEND_CHANGED | FRIEND_ACCOUNT_DELETED | SENT_STATUS | ACCOUNT_DEVICE_REPLACED | PLAN_CHANGED`). `user_id`에 FK를 두지 않는다(탈퇴 이벤트가 연쇄 삭제되지 않도록). 커밋 순서와 `seq` 순서가 다를 수 있으므로 "진행 중 트랜잭션보다 작은 seq까지만" 돌려주거나 최근 몇 초는 다음 호출에서 다시 포함(중복은 버전 비교로 무시). 90일 지난 행은 정리.
- 완료 기준: 수정 → 수신자 반영, 취소 → 수신자 상태, 삭제 후 수정이 안 내려감, 오래된 버전 무시, 동시 커밋 경계에서 누락이 없음.

### B4-04 푸시 · 서버 대체 알림 · 스케줄 작업 (설계도 8.1 · 8.3 · 13.7)
- **친구 · 시스템 푸시(8.1):** 친구 요청 도착(`send_friend_request`), 링크로 연결됨(`redeem_invite`), 다른 기기 로그인(`register_device`로 이전 기기 교체 시), 구독 만료 예정 3일 전(선택, M5).
- 푸시: Expo Push(`active_devices.push_token`). 도착 알림은 서버가 문구를 만든다 — **받는 사람의 별명을 우선 사용**(서버는 `friend_links.alias`를 알고 있음), 제목 표시 설정(`lockscreen_show_title`)과 도착 알림 설정(`notify_all`, 친구별 `notify_arrival`)을 확인한 뒤 발송. 문구는 설계도 8.3 표 그대로(예: `어머니가 일정을 보냈어요(캘린더에 자동으로 들어가요) · 병원 예약 10/3(금) 오후 3시`, 제목 숨김 시 `어머니가 일정을 보냈어요`). 수정 · 취소 · 지출도 같은 표.
- 토큰 만료 · 실패: 서버가 무효 처리, 다음 앱 실행 때 재등록(항목은 `sync`로 받음).
- **서버 대체 알림(1분마다, D-18):** 대상은 `routed_mode = ALWAYS_ADD` · `state = PENDING` · 시간 종류 `EXACT`인 전달. 오프셋은 항목의 `reminderOffsets`, 비어 있으면 받는 사람의 기본 알림(`default_reminder_offset`). 알림 시각이 지났고 **10분 이내**이며 발송 기록이 없는 것을 골라 받는 사람의 알림 설정(전체 · 친구별 일정 시각 · 잠금 화면)을 확인해 원격 푸시. 중복 방지 `fallback_pushes(delivery_id, offset, sent_at, PK(delivery_id, offset))`. 앱은 받은 항목을 저장할 때 **이미 지난 알림은 예약하지 않는다**(두 번 울림 방지).
- 스케줄: 5분마다 만료 처리(`expires_at` 지난 PENDING → EXPIRED) · 만료된 초대 링크 정리, 매일 닉네임 보류 해제 · 7일 지난 요청 지문 · 로그 정리 · 끝난 `friend_requests` 정리(pg_cron 등).
- 완료 기준: 푸시 문구 단위 시험 — 8.3 표의 서버 푸시 5상황(항상 넣기 도착 · 매번 묻기 도착 · 지출 도착 · 수정 · 취소) × 제목 표시 켜짐/꺼짐, 6.3의 "항상 확인만" 도착과 "오늘 많은 일정을 보냈어요" 문구(별명 우선 · 제목 숨김), 대체 알림 중복 방지 시험. **실기기 시험은 F4-06과 함께.**

### B4-05 공개 일정 (설계도 7.1 · 7.3 · 13.5)
- `public_events(owner_id, event_id, kind EVENT|TASK, title, time_kind, start_at, date, fuzzy_time, end_at, location, due_at, done, updated_at)`. 제목 · 시간 · 장소만(메모 · 알림 · 출처는 올리지 않음). 소유자만 쓰기, **읽기는 `can_view_events(owner_id, auth.uid())` 통과 시에만**.
- 조건: `X.visibility = PUBLIC` AND 열람자가 "전부 비공개" 대상이 아님 AND (공개 대상 방식 = 모든 친구 OR 열람자가 공개 대상에 포함) AND 서로 친구 관계가 유효(차단 · 연결 해제 아님). **가장 제한적인 설정이 이긴다.**
- `public_events_upsert` / `delete`, `friend_events(친구 id, 기간)` — 기간 최대 3개월. 비공개로 바꾸거나 지우면 **즉시 삭제**. 남에게서 받은 일정은 기본 비공개(7.1).
- 완료 기준: 조건 4개의 조합 시험(각각 하나만 어겨도 안 보임), 전환 즉시 삭제, 차단 · 연결 해제 시 조회 불가.

### B4-06 프로필 사진 저장 (설계도 5.4)
- 비공개 버킷 `avatars/{user_id}/{version}.jpg`, `avatar_upload_url`(서명 업로드 URL) → `avatar_commit`(버전 확정, **이전 파일 삭제**). 표시는 **만료되는 서명 URL**로만, **친구 관계일 때만** 사진 버전을 돌려준다. 닉네임 검색 결과 · 링크 소개 페이지에는 이니셜만. 차단한 상대의 사진은 숨김.

### B4-07 초기화 (a)(b) · 탈퇴 확장 · 운영 (설계도 3.7, 13.10)
- `reset_friend`(a): 그 친구와의 연결 해제, 주고받은 전달 기록 삭제(대기 전달은 먼저 취소), 백업 중 그 친구에게서 받은 사본 삭제. 다시 연결하면 처음부터 새로 시작.
- `reset_shared`(b): 모든 친구 관계 · 보낸 항목 기록 · 받은 전달 기록 · 초대 링크 · 공개 일정 사본 삭제, 백업 중 받은 항목 사본 · 수신함 · 삭제 기록도 삭제(복원 시 되살아나지 않게). 계정 · 개인 기록 백업 · 구독은 유지.
- **`backup_delete_all` 확장(M2 B2-03 이어서):** `scope = 'PERSONAL'`일 때 개인 기록 백업과 함께 **`public_events` 행(공개 일정 사본)도 삭제**한다(D-5 권장 범위, 받은 항목 사본 · 수신함 · 삭제 기록은 유지).
- **`delete_account` 확장(M2 B2-04 이어서):** 친구들에게 `FRIEND_ACCOUNT_DELETED` 기록 → 아직 전달되지 않은 항목 취소 → 프로필 사진 삭제 → 닉네임 보류 → auth 삭제(연쇄). 이미 전달된 항목은 상대 폰에 남고 보낸 사람 표시가 "탈퇴한 사용자"(D-14, 수신 폰의 `sender_state = DELETED`).
- 운영: 모든 함수는 요청 추적 id · 결과 코드 · 걸린 시간만 기록(**일정 제목 · 메모 · 금액 · 입력 문장 · 토큰은 로그 금지**). 신고 처리는 대시보드/간단한 관리자 화면에서(사진 삭제 · 닉네임 초기화 · `profiles.status` 정지), 목표 처리 24시간.

### B4-08 RLS · IDOR 시험 일괄 (설계도 13.8, 16.2)
- 다른 사용자의 `shared_items` · `deliveries`를 id로 조회해도 결과가 없다(`shared_items`는 보낸 사람과 수신자만, `deliveries`는 수신자만). `friend_links`는 `owner_id = auth.uid()` 행만. 교체된 이전 기기 세션의 쓰기 거부. 서비스 키는 앱 번들에 없다.

## 앱 단위 (F)

### F4-01 마이그레이션 005 (설계도 12.3 중 M1에서 미룬 부분 — README 5.1)
- `events` · `tasks` · `transactions`에 공통 추가: `origin('LOCAL'|'RECEIVED'|'COPIED') DEFAULT 'LOCAL'`, `shared_item_id`, `delivery_id`, `sender_user_id`, `sender_name`, `sender_state('ACTIVE'|'DISCONNECTED'|'DELETED')`, `remote_version`, `sender_edited_at`, `sent_copy_of`.
- 새 테이블: `friends_cache`, `inbox_items`, `sent_items_cache`, `sent_deliveries_cache`, `received_tombstones`. 기존 데이터 보존 · 재적용 안전 시험(M1-01과 같은 방식).
- **항목에는 보낸 사람 id만 연결하고 표시할 때 이름(별명)을 찾는다** — 별명을 바꾸면 이미 받은 항목의 표시도 즉시 바뀐다(5.2).

### F4-02b 받은 항목 · 수신함 · 삭제 기록의 백업 · 복원 (설계도 3.6 · 12.4, M2 B2-03 · F2-04 · F2-05 확장)
- 받은 항목 사본(`RECEIVED_COPY`), 수신함(`INBOX`), 삭제 기록(`TOMBSTONE`)을 **F2-04의 outbox · 백업 업로더에 추가**한다(같은 `backup_upsert`, `entity_type`은 M2 B2-03에서 이미 허용).
- 복원(F2-05)에서 이 세 가지도 되살린다. 복원 순서: 개인 기록 → 받은 항목 사본 · 수신함 → **삭제 기록(`received_tombstones`)을 마지막에 적용해 지운 항목이 되살아나지 않게** 한다.
- 시험: 앱 삭제 → 재설치 → 복원 후 받은 항목 · 수신함이 그대로이고, 지웠던 받은 항목이 다시 나타나지 않음. 초기화 (b) 뒤에는 이 세 가지도 비어 있음(B4-07).

### F4-02 동기화 엔진 (설계도 12.4)
- 다운로드: 앱 시작 · 포그라운드 전환 · 푸시 수신 · 당겨서 새로고침 때 `sync?cursor=`. 커서를 `sync_state`에 저장.
- **받은 전달 처리 순서:** 삭제 기록 확인(있으면 무시하고 ack) → 서버가 정한 `routed_mode`대로 처리(`ALWAYS_ADD`: 캘린더 · 지출에 저장 / `ASK`: 받은 카드 / `ALWAYS_VIEW`: 수신함) → 알림 예약(**이미 지난 알림은 예약하지 않음**) → ack.
- 같은 `shared_item_id`의 **더 높은 버전은 덮어쓰기**, 같거나 낮으면 무시. 삭제 후 도착한 수정은 무시(삭제 기록).
- **시작 시각이 이미 지난 받은 일정**(만료 직전 가져간 경우): 캘린더에 넣되 알림 없음, 상태 `PAST`(6.3, 15).
- **시간 종류가 `EXACT`가 아닌 받은 일정(종일 · 대략적 시간)은 기본 알림도 예약하지 않는다**(D-3). 서버 대체 알림도 `EXACT`만 대상(B4-04).
- 저장은 저장소 계층 경유, ActionLog 출처는 "동기화"(12.1).
- 시험: 순서(삭제 기록 → 처리 → 알림 → ack), 버전 비교 3종(높음 · 같음 · 낮음), 지난 일정, 같은 delivery 중복 도착(멱등).

### F4-03 사람 탭(P1) · 친구 추가(P2) · 링크 결과(P3) (설계도 5.1, 11.2)
- P1: 친구 목록(사진 · 별명 · 작은 글씨 닉네임), 받은 친구 요청, 수신함 · 보낸 항목 바로가기, [친구 추가]. 상태 4종 모두(비어 있음 · 불러오는 중 · 오류 + 다시 시도 · 오프라인). 친구 30명 도달 시 [친구 추가] 비활성 + 안내.
- P2 시트 탭 3개: **링크**(만들기 · 공유 시트 · **남은 시간 표시** · 만료되면 [새 링크 만들기], 1명 1회용 5분) / **QR**(같은 링크를 QR로, 스캔 — 카메라 권한, `expo-camera` 계열 설치) / **닉네임**(정확 입력 → 결과 1명 → [친구 요청 보내기], 상대 수락 필요).
- 링크 열기: `expo-linking` + Universal Links / App Links. P3 결과 문구 8종(정상 · 만료 · 이미 사용됨 · 이미 친구 · 내 링크 · 차단 관계 · 30명 초과(내 쪽/상대 쪽) · 오프라인)은 설계도 5.1 표의 문구 그대로. **오프라인이면 토큰을 사용 처리하지 않는다.** 로그인하지 않은 상태로 열면 로그인 → 닉네임 → (5분 이내면) 자동 연결, 이미 만료면 만료 안내. 앱이 없으면 소개 웹페이지(M0-03)에서 스토어 안내.
- 연결되면 초대한 사람에게 "OO님과 연결됐어요" 알림과 [연결 끊기].
- **실기기:** 링크 탭 → 앱이 열려 자동 연결(iOS · Android), QR 스캔.

### F4-04 보내기 시트(S1) · 보낸 항목(S2) · 음성으로 보내기 (설계도 6.2 · 6.5 · 6.6 · 4.6 · 15, 시안 `#sendSheet`, `#sentSheet`) — 하위 단위: (a) S1 시트와 검증 / (b) 오프라인 outbox · 결과 · [다시 보내기] / (c) S2 보낸 항목 수정 · 취소 / (d) 음성으로 보내기
- **진입점(M1에서 미룬 연결):** 일정 상세(K2) · 지출 상세(E2)의 [보내기]와 친구 상세 [보내기]가 S1을 연다(시안 `startSend`).
- S1 필드: 받는 사람 칩 다중 선택("받지 않기" 친구는 비활성 + "이 친구는 받기를 꺼 두었어요"), 일정(제목 필수 · 날짜 필수 · 시간: 정확 / 대략 / 종일(D-4) · 종료 시각 · 장소), 지출(금액 필수 · 카테고리 · 메모 · 날짜 · 시간), 알림(다중, 비우면 받는 사람 기본 알림 — **시간이 정확한 일정일 때만 표시, 대략 · 종일이면 숨김**), **"내 캘린더에도 넣기"**(기본 꺼짐, 설정 > 보내기 기본값으로 변경, 지출은 "내 지출에도 넣기"), 켜면 **독립 복사본**이고 한쪽을 고쳐도 다른 쪽은 안 바뀐다는 안내 한 줄.
- 남은 횟수: 무료 "공유 체험 1회 남음", 구독자 "오늘 보낼 수 있는 건수 N건"을 **한도의 80%(40건) 이상일 때만** 표시.
- 보내기 결과: 수신자별 "보냈어요" 또는 실패 사유, 일부 실패면 **실패분만 [다시 보내기]**. 사유 문구: `NOT_AVAILABLE` "보낼 수 없는 상대예요", `PAST_EVENT` "이미 지난 일정은 보낼 수 없어요", `DAILY_LIMIT` "오늘은 더 보낼 수 없어요(자정에 초기화)", `NOT_ENTITLED`/`TRIAL_USED` → 구독 안내.
- **오프라인에서도 [보내기]를 누를 수 있다**: outbox에 넣고 `clientRequestId`를 **넣는 시점에 고정**, 보낸 항목에 "보내는 중"으로 표시, 연결되면 자동 전송, 나중에 한도 · 관계 · 시각 경과로 실패하면 "보내지 못했어요(사유)" + 알림 1회(15). 시안 `submitSend`, `flushOutbox`.
- S2 보낸 항목: 목록 + 수신자별 상태 4종, [수정] · [취소]. 수정 범위는 **확인 필요(README 3.1 #2)** — 시안은 제목 · 날짜 · 시간만, 설계도 6.5는 범위를 제한하지 않으므로 확정 전에는 보내기 시트와 같은 필드(지출은 금액 · 카테고리 · 메모 포함)로 구현하는 쪽이 안전하다. 수정은 D-7에 따라 **오프라인 비활성**, 취소는 **2단계 확인** + 오프라인 비활성, 구독이 만료돼도 허용. "수정됨" 태그.
- 음성으로 보내기(4.6): AI가 `SEND_EVENT` / `SEND_EXPENSE`를 돌려주면 **저장하지 않고 S1을 연다.** 수신자 매칭은 **폰에서** 친구 별명 · 닉네임과 비교(친구 목록은 AI에 보내지 않음). 이름 없음 → 친구 목록에서 선택, 같은 이름 여럿 → 선택, 일치 없음 → 목록에서 선택, 여러 명("민수랑 지은이한테") 가능. `includeInMyCalendar`가 true면 토글이 켜진 채 열림. 무료는 체험(AI 1회 + 공유 1회, 수신자 1명, 일정만), 체험이 없으면 구독 안내.
- 시험: 오프라인 → 연결 순서 · 멱등 재전송, 부분 실패 재전송, 80% 표시 경계, 시작 시각이 지난 일정 거부, 설계도 4.6 예시 문장.

### F4-05 받은 항목(R1) · 수신함(R2) (설계도 6.3 · 6.5, 11.3)
- **M1에서 미룬 연결:** 홈의 받은 항목 배지(M1-07), 지출 월 합계의 "받은 지출 포함" 반영(M1-15), 엑셀 내보내기의 출처 "OO님이 입력"(별명 적용, 설계도 5.2 · M1-13).
- R1 받은 카드: 보낸 사람 아바타 · 이름(별명) 항상 표시, 내용, **[캘린더에 넣기] [확인만]** + "OO님 일정은 항상 이렇게" 체크(체크하고 누르면 그 친구의 모드가 `ALWAYS_ADD` / `ALWAYS_VIEW`로 바뀜). 지출은 합계 포함 토글.
- R2 수신함: "확인만" 항목 30일 보관, **남은 일수** 표시, [넣기] · [삭제]. 30일이 지나면 자동 삭제.
- 수정된 항목 "수정됨 · 10/2 15:30" 태그(눈에 띄게), 취소된 항목 취소선 + "취소됨", 보낸 사람 탈퇴 시 "탈퇴한 사용자"(D-14).
- **받은 항목 카드의 보낸 사람 이름을 길게 누르면 별명 편집**(5.2의 세 번째 진입점). 이름 표시는 `friends_cache.alias` 조회, `sender_name`은 친구 관계가 끊겨 조회할 수 없을 때의 마지막 이름 보관용이고, 보낸 사람이 탈퇴하면 "탈퇴한 사용자"로 표시한다(D-14 · D-17).
- 받은 항목 삭제는 **오프라인에서도 즉시**(폰 안) + 삭제 기록을 outbox로. **한 사람 것 일괄 삭제**는 친구 상세 > "이 친구에게서 받은 항목 모두 삭제" → 2단계 확인.
- 받은 지출은 기본 합계 포함(항목별 토글 · 친구별 기본값). 받은 일정의 공개 기본값은 비공개(7.1).
- 시험: 모드 4종 × 일정 · 지출, "항상 이렇게" 체크 결과, 30일 만료, 삭제 기록 후 수정 무시, 일괄 삭제.

### F4-06 푸시 등록 · 처리 (설계도 8.1)
- `expo-notifications`로 푸시 토큰을 얻어 `register_device`에 전달(로그인 직후 · 토큰 갱신 시). 포그라운드 수신 시 `sync`, 알림을 누르면 해당 받은 카드/수신함으로 이동.
- **실기기 시험(필수):** 앱 포그라운드 · 백그라운드 · **완전 종료** 각각에서 도착 알림, 배터리 절약 모드, 서버 대체 알림이 정시에 울리는지(D-2).

### F4-07a 공개 일정 동기화 (설계도 7.1 · 12.4 · 13.5)
- 내 일정 · 할 일의 공개 값(`PUBLIC`)이 바뀌면 outbox로 `public_events_upsert`(공개로 전환 · 공개 항목 수정), 비공개 전환 · 삭제는 **즉시 `public_events_delete`**(오프라인이면 outbox에 쌓되 연결 복귀 시 가장 먼저 처리). M4 처음 진입 때 이미 공개인 기존 항목은 **일괄 1회 업로드**.
- 남에게서 받은 일정은 기본 비공개. 시험: 전환 즉시 삭제, 오프라인에서 비공개로 바꾼 일정이 복귀 후 서버에서 지워짐.

### F4-07 알림 설정(T3) · 공개 범위(T4) · 친구 상세(P5) · 친구 일정(P6) · 겹쳐 보기 (설계도 8.2 · 7.1 · 7.2 · 5.2) — 하위 단위: (a) T3 · T4 / (b) P4 · P5 / (c) P6 · 겹쳐 보기
- T3: 전체 · 나(기본 알림) · **친구별(도착 알림 · 일정 시각)** · 잠금 화면 제목 표시 · 권한 상태. **도착 알림 · 잠금 화면 설정은 서버에도 저장**(서버가 문구를 만듦; `update_profile_settings`, 기본 알림 오프셋 · `audience_mode` 포함 — M2 F2-09의 동기화 규칙). 우선순위는 M1-09 함수.
- T4: 새 일정 기본 공개, 공개 대상 방식(모든 친구 / 선택한 친구 → 친구마다 공개 대상 체크), 친구별 "전부 비공개".
- P5 친구 상세: 사진 · 닉네임 · **별명 편집**(1~20자, 한글 · 영문 · 숫자 · 공백 · 이모지, 중복 허용 → 음성 매칭은 선택 화면, 지우면 닉네임으로 복귀, 상대에게 알리지 않음), 일정 받기 설정, 지출 받기 설정(4모드), 이 친구 알림 설정, 공개 범위, 받은 항목 모두 삭제, 연결 끊기(2단계, 상대에게 알림 없음, 오프라인 비활성), 차단(체크박스 "이 사람에게서 받은 항목도 삭제" 기본 꺼짐), 신고. 이름 아래에 실제 닉네임을 작게 함께 표시.
- **처음 연결될 때(P4):** "이 사람을 뭐라고 부를까요?"(건너뛰기 가능, 기본값 닉네임) + 일정 · 지출 각각 [매번 물어보기(기본)] [항상 캘린더에 넣기] [항상 확인만]. 건너뛰면 매번 묻기(5.3).
- P6: 그 친구의 공개 일정 월간 캘린더(읽기 전용, 할 일은 날짜 아래 목록), **[내 캘린더에 복사]**(구독 불필요, 출처 "OO님 일정에서 복사", `origin = COPIED`). 내 캘린더의 "친구 일정 겹쳐 보기": 친구 **최대 3명**, 서로 다른 색 점 + 이름 · "겹침" 문구(색만으로 구분 금지).
- 완료 기준: 설계도 7.1 조건 4개 중 하나만 어겨도 그 일정이 안 보임(서버 시험과 앱 화면 모두).

### F4-07b 설정(T1)의 "보내기" · "친구 · 차단" 섹션 (설계도 10.1)
- 보내기: "보낼 때 내 캘린더(지출)에도 넣기" 기본값 토글(F4-04가 읽는 값, 백업 대상 3.6).
- 친구 · 차단: 친구별 받기 설정 요약(일정 · 지출 모드), 차단 목록으로 이동.

### F4-08 프로필 사진(T2) (설계도 5.4)
- 갤러리 선택 · 카메라 촬영(권한 문구는 한국어, M6). **크롭 화면:** 원형 가이드, **핀치 확대 · 드래그**(`react-native-gesture-handler` + `react-native-reanimated` 등, 설치 시 보고), [완료].
- 저장: 기기에서 **512×512 정사각 JPEG(품질 약 0.8)** 로 줄이고 **EXIF 제거**(위치 정보) 후 업로드. 크기 요구사항은 사용자에게 보이지 않는다. 기본 아바타 = 별명(또는 닉네임) 첫 글자 이니셜. 변경 · 삭제 가능.
- 업로드 실패: 이전 사진 유지 + [다시 시도](15).
- **실기기:** 핀치 · 드래그가 부드럽게 동작, EXIF가 실제로 제거됨(결과 파일 확인).

### F4-09 차단 목록 · 신고(T8) · 초기화 (a)(b) (설계도 5.2 · 3.7)
- 차단 해제는 설정 > 차단 목록, 신고 사유 선택(부적절한 프로필 사진 · 닉네임 · 스팸 / 원치 않는 전송 · 기타 + 설명) → 서버 접수, 신고하면서 차단도 가능.
- 초기화 (a)(b): 3.7 표대로, 2단계 확인, 오프라인 비활성(받은 항목의 폰 내 삭제만 예외, 4.2).
