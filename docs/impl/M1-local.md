## 작업 단위

### M1-01 도메인 확장 · 마이그레이션 003 (설계도 12.3, 13.4)
- `domain/event/event.ts`: `EventTime`에 종일 추가. 설계도 13.4와 맞춘다 — `{ kind: 'ALL_DAY'; startAt: null; fuzzyTime: null }`. 날짜는 `date: string`(`YYYY-MM-DD`, 이벤트의 `timezone` 기준)을 **모든 종류에 공통 필드가 아니라 ALL_DAY · FUZZY에만** 둔다(EXACT는 `startAt`으로 충분). 기존 FUZZY는 날짜가 없으므로 같이 추가.
  - 시안은 편의상 종일의 `startAt`을 그날 23:59로 저장한다. **앱에서는 위 정의를 따르고**, 서버 만료 계산용 `starts_at`(그날 23:59 KST)은 M4 서버가 `date`로 만든다(13.3).
- `Event` · `Task`에 `visibility: 'PUBLIC' | 'PRIVATE'`(기본 `PRIVATE`), `Transaction`에 `includeInTotal: boolean`(기본 true) · `bundleItems: string[] | null`.
- 출처(`origin` 등 12.3 공통 컬럼)는 **M4에서** 추가한다(받은 항목이 생길 때). M1에서는 `origin = 'LOCAL'` 고정이므로 지금 넣지 않는다.
- `Reminder`에 `lastError: string | null`(예약 실패 사유, 기본 null)을 추가한다(M1-08의 "예약 실패" 표시 근거).
- 마이그레이션 `003-events-tasks-ext.ts`: reminders에 `last_error TEXT NULL`; events에 `date TEXT NULL`, `visibility TEXT NOT NULL DEFAULT 'PRIVATE'`; tasks에 `visibility`; transactions에 `include_in_total INTEGER NOT NULL DEFAULT 1`, `bundle_items TEXT NULL`; `settings(key PRIMARY KEY, value)` 테이블. 기존 데이터에 기본값이 들어가야 한다.
  - **events 테이블은 다시 만든다**(새 테이블 생성 → 복사 → 옛 테이블 삭제 → 이름 변경 → 인덱스 재생성). 001의 `time_kind` CHECK가 `EXACT|FUZZY`만 허용하고 SQLite는 CHECK를 `ALTER`로 바꿀 수 없기 때문이다(구현 중 확인, 2026-10-03). 모양 검사: EXACT는 `start_at` 있음 · `fuzzy_time` · `date` 없음 / FUZZY는 문구 있음 · `start_at` 없음 · `date`는 비어도 됨(기존 행) / ALL_DAY는 `date` 있음 · `start_at` · `fuzzy_time` · `end_at` 없음.
  - 기존 FUZZY 일정의 `date`는 `NULL`로 둔다(추측하지 않음). **새로 저장하는 FUZZY의 날짜 필수 검사는 검증기(M1-02 · M1-04)에서 한다.**
  - `settings.value`는 JSON 텍스트(`json_valid` 검사)로 저장하고 `updated_at` 컬럼은 두지 않는다(설계도 12.3에 없는 컬럼 금지).
- 시험: 001 · 002로 만든 DB에 기존 지출 · 일정 · 할 일을 넣고 003을 적용 → 데이터 보존, 기본값 확인, 두 번 적용해도 안전(`migrate.ts`의 버전 관리), 새 제약이 잘못된 값을 거부, **중간 실패 시 전체 롤백(버전 2 유지)**.
- 완료 기준: 타입 검사 통과, 기존 시험 전부 통과, 새 마이그레이션 시험 통과.

### M1-02 일정 · 할 일 · 알림 저장소와 실행기 (설계도 12.2)
- 저장소: 이미 있는 `database/repositories/sqlite-{event,task,reminder}-repository.ts`를 M1-01 필드에 맞게 확장.
- 실행기(신규, `application/executor/`): `create-event`, `update-event`, `delete-event`(소프트 삭제 `deletedAt`), `complete-event`, `create-task`, `update-task`, `complete-task`, `delete-task`, `create-reminder`, `cancel-reminder`. 지출 실행기(`create-transaction-executor.ts`)의 구조(제안 → 검증 → 단일 트랜잭션 → ActionLog)를 따른다.
- 검증기(`application/validator/`): 종료 시각이 시작 시각 뒤, 상대 알림은 **정확한 시각이 있는 일정에만**(종일 · 대략적 시간에는 붙일 수 없음, D-3), 시각은 UTC ISO, 제목 필수(1~100자), 장소 100자.
- 상태: 시간이 지나면 `PAST`(자동 `COMPLETED` 금지, `event.ts` 주석 규칙 유지).
- **되돌리기:** 일정 · 할 일 · 리마인더 실행기의 되돌리기를 `application/undo`에 이 단위에서 추가한다(지출만 있음). M1-05 · M1-06 · M1-11의 [되돌리기] 버튼은 이 로직을 화면에 연결하기만 한다.
- 시험: 실행기별 정상/검증 실패/되돌리기, 종일 일정에 알림 요청 시 거부.
- 완료 기준: 위 실행기가 저장소 계층만 거쳐 동작하고 UI는 아직 없어도 된다.
- **결정(2026-10-04, 앱 소유자):**
  1. 되돌리기는 ActionLog에 새 동작 `UNDO_ACTION` 하나로 기록한다(payload: `undoOf { undoId, actionId }`, `actionType`). 동작별 역동작(`RESTORE_*`)은 만들지 않는다.
  2. `PAST`는 DB에 저장하지 않고 읽을 때 순수 함수 `eventLifecycleStatus(event, now, 일정 시간대의 오늘 날짜)`로 계산한다. EXACT는 종료(없으면 시작) 시각이 지나면, ALL_DAY · 날짜 있는 FUZZY는 일정 시간대 기준 그 날짜가 지나면 `PAST`. 날짜 없는 옛 FUZZY는 바뀌지 않는다. `COMPLETED` · `CANCELLED`는 그대로이며 자동 `COMPLETED`는 없다.
  3. 일정 · 할 일을 완료해도 남은 알림은 취소하지 않는다(설계도에 규칙 없음, README 3.1 #19).
  4. 상대 알림 오프셋은 "정수이고 0 이하"만 검사한다. 고를 수 있는 값 목록은 M1-04 입력 폼에서 제한한다.
- 구현 메모: 리마인더 생성 · 재계산 · 복구 결과는 항상 `REQUESTED`(OS 예약은 M1-08). 일정 시각 변경 시 상대 알림의 `fireAt`을 다시 계산하고, 종일 · 대략적 시간으로 바뀌거나 삭제되면 연결된 알림을 `CANCELLED`로 바꾼다. `UPDATE_EVENT`로 `CANCELLED` 상태를 만드는 기능과 `UPDATE_REMINDER`는 이 단위에 없다.

### M1-03 시간 해석 규칙 코드 (설계도 4.3 · 4.4, 시안 `mockInterpret` 참조)
순수 함수 모듈(예: `application/proposals/clock-time-rules.ts`). 외부 의존 없이 만들어 M3 서버(게이트웨이)가 같은 시험 벡터로 같은 결과를 내도록 한다. **서버(`server/`는 의존성 없는 `.mjs`)와 앱(TS)은 이 모듈을 공유할 수 없으므로 서버는 별도 구현이다. 두 구현이 같은 결과임을 보장하는 수단은 아래 시험 벡터를 담은 `docs/impl/time-vectors.json`(이 단위에서 만든다, 필수)을 앱 시험과 서버 시험(M3-B3-04)이 같은 값으로 쓰는 것이다.**

입력: `{ now(UTC ISO), timeZone('Asia/Seoul'), dayOffset(0=오늘, 1=내일 …), hour, minute, meridiem?: 'AM' | 'PM' | null, confirmedNextDay?: boolean, kind: 'EVENT' | 'EXPENSE' }`. `confirmedNextDay`는 "내일로 할까요?"에 [예]를 눌렀다는 뜻으로, 켜면 `dayOffset + 1`에 "내일 이후" 규칙을 적용하되 7~11시를 오후로 확정한다. 출력: `{ status: 'OK', at(UTC ISO), autoMeridiem } | { status: 'ASK_MERIDIEM' } | { status: 'ASK_TOMORROW' } | { status: 'ASK_YESTERDAY' }`(지출에서 오늘 오전 N시가 아직 안 왔을 때). 시험 벡터 JSON도 이 필드 이름을 그대로 쓴다.

규칙(단서가 없을 때만. 단서가 있으면 그대로: "저녁 7시" = 19:00):

| 상황 | 결과 |
| --- | --- |
| 일정, 오늘, 지금 이후 가장 가까운 시각 | 오전 N시가 안 지났으면 오전, 지났으면 오후. 오후도 지났으면 `ASK_TOMORROW`("오늘 N시는 이미 지났어요. 내일로 할까요?") |
| 일정, 내일 이후, 1~6시 | 오후(13~18시), `autoMeridiem: true` |
| 일정, 내일 이후, 7~11시 | `ASK_MERIDIEM` |
| 12시 | 낮 12시. 오늘이고 이미 지났으면 질문 |
| "N시 반" | 같은 규칙에 30분 더함 |
| 13~23시, 0시(24시간제) | 그대로, 오전/오후 판단 없음. "0시"·"자정" = 말한 날짜의 다음 날 00:00(D-10) |
| 지출(이미 쓴 돈) | 일정과 반대로 **지금 이전**의 가장 가까운 시각. 오늘 오전 N시가 아직 안 왔으면 어제로 보지 않고 질문 |
| "내일로 할까요?"에 [예] | 다음 날 같은 숫자 시각에 "내일 이후" 규칙을 적용하되 7~11시는 **오후로 확정**(되묻지 않음) |

시험 벡터(설계도 4.3 · 14.6의 표 + 아래 "보강" 표시 행. 기준 시각은 KST). **"보강" 행은 설계도에 없는 추가 예시이므로 앱 소유자 승인 후 시험에 넣는다**(`CLAUDE.md`: 시험 문장은 설계도 4장 예시):

| 문장(시각 부분) | 기준 시각 | 기대 |
| --- | --- | --- |
| 친구랑 7시 약속 | 06:30 | 오늘 07:00, autoMeridiem true |
| 친구랑 7시 약속 | 07:10 | 오늘 19:00, autoMeridiem true |
| 친구랑 7시 약속 | 20:00 | ASK_TOMORROW |
| 위 질문에 [예]("내일로") | 20:00 | 내일 19:00(7~11시도 되묻지 않고 오후로 확정, 4.3 · 4.4) |
| 7시에 밥 7000원 먹었어(지출) | 20:00 | 오늘 19:00 |
| 친구랑 19시 약속 | 10:00 | 오늘 19:00, autoMeridiem false |
| 내일 3시 치과 | 아무 때 | 내일 15:00, autoMeridiem true |
| 내일 9시 회의 | 아무 때 | ASK_MERIDIEM |
| 12시에 약속 (보강: "점심"은 오전/오후 단서이므로 쓰지 않음) | 오늘 13:00 | ASK_TOMORROW(이미 지남) |
| 내일 7시 반 (보강) | 아무 때 | ASK_MERIDIEM(7~11시) |

| 내일 0시 (보강) | 오늘이 10월 3일 | 10월 5일 00:00(말한 날짜 "내일 = 4일"의 다음 날 00:00, D-10 권장안. 결과 카드에 "10월 5일 0시"로 풀어서 표시) |

- 이 모듈은 **로컬 파서가 일정을 해석하는 데 쓰지 않는다**(무료 일정 입력은 직접 입력 폼, 설계도 4.2 확정). 직접 입력 폼은 시간 선택기를 쓰므로 해당 없음. M3에서 서버가 AI의 `hour/minute/meridiemExplicit/상대 날짜`로 최종 시각을 계산하는 규칙의 **기준 구현**이다. 앱은 서버 응답의 시각을 이 모듈로 **재계산하지 않고** 구조만 검사한다(UTC ISO · 지난 시각 여부 · `autoMeridiem` 표시값, M3 F3-01) — 최종 시각 계산은 한 곳(서버)에서만 한다는 `AGENTS.md` 원칙.
- 완료 기준: 위 벡터 전부 통과, 경계(자정 넘김 · 월말 · 윤년 2월 29일) 시험.
- 구현 메모(2026-10-04): 모듈 `application/proposals/clock-time-rules.ts`의 `resolveClockTime`, 벡터 `docs/impl/time-vectors.json`, 시험 `scripts/verify-clock-time-rules.cjs`. 시간대 계산은 `Intl.DateTimeFormat`을 쓴다(Node에서만 확인, 실기기 Hermes 미확인). 벡터 파일의 `vectors`는 모두 시험에 쓰인다. 위 표의 "보강" 3행(12시 · 내일 7시 반 · 오전 6시 지출)은 2026-10-04 앱 소유자 승인으로 `vectors`(group `supplement`)로 옮겼다. "내일 0시"는 D-10 지시에 따라 `vectors`에 있다. 표에 없어 정한 것: ① 오전 12시는 "0시"·"자정"과 같게 말한 날의 다음 날 00:00(2026-10-04 앱 소유자 지시로 변경, 벡터 `am12-01` · `am12-02`) ② 지출에서 날짜를 말했는데 단서가 없으면(어제 7시) `ASK_MERIDIEM` ③ 일정에서 `dayOffset < 0`은 "내일 이후" 규칙 ④ 단서가 있거나 24시간제면 지난 시각이어도 그대로 돌려줌(지남 판단은 호출하는 쪽) ⑤ `[예]` 뒤 7~11시를 오후로 확정한 결과의 `autoMeridiem`은 true ⑥ `hour`는 0~23만 받고 그 밖은 `RangeError`.

### M1-04 일정 직접 입력 폼 (H4 일정 탭, 시안 `#editSheet`)
- 필드: 제목(필수), 날짜, **시간 종류 3택 — 정확한 시각 / 대략적 시간 / 종일**, 종료 시각(정확한 시각일 때만, 선택), 장소, 알림(다중: 정시 · 10분 전 · 30분 전 · 1시간 전 · 하루 전. 정확한 시각일 때만), 공개 토글(로그인 사용자만 보임. 게스트는 항상 비공개 · 항목 없음, 설계도 3.3).
- 대략적 시간(FUZZY): "저녁쯤" 같은 문구 입력 + 날짜. 문구는 비어 있으면 저장 불가.
- 말한 문장으로 열면 제목에 문장을 미리 채운다(최대 100자).

- 시험: 3종 저장/수정, 종료<시작 거부, 종일 + 알림 선택 불가, 공개 기본값 적용(게스트=비공개).
- 완료 기준: 시안과 같은 화면, 200%에서 잘림 없음, 접근성 이름 부여.
- 구현 메모(2026-10-04): 화면 `features/calendar/entry-form-screen.tsx`(경로 `/entry-form`, 약속 · 할 일 공용), 폼 → 제안 변환 `application/planner/event-form.ts`, 일정 · 할 일 공용 서비스 `application/planner/planner-services.ts`(저장 → 알림 요청 → 되돌리기 바), 시험 `scripts/verify-planner-services.cjs`. ① **기본 알림은 새 일정 폼에서 미리 선택**되어 있고 사용자가 해제할 수 있다(해제하면 알림 없음, 시안 `editExtra.reminders`와 같음). 문장으로 말한 알림이 없을 때 기본 알림을 붙이는 쪽은 M3. ② 종료 시각은 같은 날짜만 입력할 수 있다(다른 날로 넘어가는 종료는 폼에서 다루지 않음). ③ 저장했지만 알림 일부가 실패하면 폼을 닫지 않고 "저장했어요, 확인할 것이 있어요" 목록을 보인다(부분 성공 표시). ④ 이 단위에서 글자 크기 헬퍼(`utils/font-scale.ts`)와 설정 저장소(`application/settings`, `settings` 테이블)를 먼저 만들었다(M1-12 · M1-14 몫, 새 화면이 `scaleFont`를 쓰기 때문). ⑤ 날짜 · 시간 입력은 모바일에서 시스템 선택기, 웹에서 글자 입력이다(`picker-field.web.tsx`).

### M1-08 로컬 알림 어댑터 (설계도 8.1 · 8.2 · 8.3, 15)
- 설치: `npx expo install expo-notifications`(패키지 이름 · 사유를 보고).
- 어댑터 인터페이스(`application/` 쪽에 정의, 구현은 `adapters/notifications/`): `requestPermission()`, `getPermissionState()`, `schedule(reminder) → 'SCHEDULED' | 'PERMISSION_BLOCKED' | 'FAILED'`(`FAILED`는 어댑터 반환값일 뿐, 저장 상태는 `REQUESTED` + `lastError`), `cancel(reminderId)`, `refillNearest()`.
- 리마인더 `status`는 **예약 성공 후에만 `SCHEDULED`**. 권한이 없으면 `PERMISSION_BLOCKED`로 저장하고 일정 카드에 "알림 꺼짐". 예약이 실패하면 일정은 저장 · 알림은 "예약 실패, 다시 시도" 표시(15). 성공으로 표시하지 않는다.
- 오프셋은 **음수 = 시작 전, 0 = 정시**(D-15). 일정 시각이 바뀌면 상대 오프셋(`relativeOffsetMinutes`)으로 `fireAt`을 다시 계산해 재예약.
- **iOS 로컬 알림 64개 한도 대응:** 항상 가까운 순으로만 예약하고, 앱 실행 · 포그라운드 전환 때 부족분을 다시 채운다. 예약하지 못한 리마인더는 `REQUESTED`로 남는다. **한도 때문에 아직 예약하지 않은 것은 `lastError = null`, 예약 시도가 실패한 것은 `lastError`에 사유**를 적어 둘 구분하고, "예약 실패, 다시 시도" 표시는 `lastError`가 있는 것에만 보인다(`ReminderState`에 새 값을 추가하지 않는다).
- 문구: 제목 표시 켜짐 `병원 예약 · 30분 후 (강남세브란스)`, 꺼짐 `일정 알림 · 30분 후`(8.3). 잠금 화면 제목 표시 설정(`settings.lockscreenShowTitle`, 기본 켜짐)을 따른다.
- Android: 알림 채널 생성, Android 13+ `POST_NOTIFICATIONS` 요청, 정확한 알람(`SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`) 정책은 **확인 필요** — 공식 문서로 확인한 결과를 보고하고(M6에서 사유 기재), 확인 전에는 정확한 알람이 항상 가능하다고 가정하지 않는다.
- 시험(자동): 어댑터를 가짜로 바꾼 상태에서 상태 전이(REQUESTED → SCHEDULED / PERMISSION_BLOCKED / 실패), 64개 초과 시 가까운 순 선택, 시간 변경 시 재계산.
- 완료 기준: **실기기(iOS · Android)에서 정시 · 10분 전 알림이 울리고, 앱을 종료해도 울림.**(배터리 절약 모드 포함 확인)

### M1-09 알림 우선순위 함수 (설계도 8.2, 시안 `itemSilentReason`)
순수 함수 `resolveSilence({ allOn, ownOn, permission, friendNotifyEventTime, isReceived })`:
1. `allOn = false` → "모든 알림이 꺼져 있어요" (가장 먼저)
2. 권한 `BLOCKED` → "기기의 알림 권한이 꺼져 있어요"
3. `ownOn = false`(내 일정) → "내 일정 알림이 꺼져 있어요"
4. 받은 일정이고 그 친구의 `notifyEventTime = false` → "OO님 일정의 시각 알림을 꺼 두었어요"(이름은 별명 우선)
5. 아니면 알림이 울림.
- 더 제한적인 설정이 이긴다(전체 끔 > 친구별 > 항목별). 문장에서 따로 말한 알림은 기본 알림보다 우선한다.
- 시험: 위 5가지 + 조합(전체 끔과 개별 켜짐 → 전체 끔 사유가 표시되어야 함).
- 구현 메모(2026-10-04): 모듈 `application/notifications/resolve-silence.ts`(`resolveSilence`는 사유 코드를 돌려주고 문구는 `describeSilence`가 만든다), 시험 `scripts/verify-resolve-silence.cjs`. 이 함수는 3번 `ownOn`을 **내 일정에만**, 4번을 **받은 일정에만** 적용한다(명세 문구 그대로). 시안의 `itemSilentReason`은 `ownOn`을 받은 일정에도 적용하므로 시안과 다르다 — 앱 소유자 확인 필요. `permission` 값은 `GRANTED | BLOCKED | UNDETERMINED`로 두었고 `BLOCKED`만 알림을 막는다(M1-08 어댑터가 같은 값을 쓰도록 맞춘다). "문장에서 따로 말한 알림이 기본 알림보다 우선"은 이 함수의 범위가 아니라 기본 알림을 붙이는 쪽(M1-04 · M1-11)에서 처리한다.

### M1-10 온보딩 O1 · O2 · 로그인 선택 화면 자리 (설계도 3.2)

### M1-11 결과 카드(H2) 로컬 경로 · 되돌리기 · 중복 지출 (설계도 4.2 · 11.3 · 15)
- 로컬 파서 성공 → 자동 저장 + 카드(지출) + [되돌리기](화면 아래 **되돌리기 바**, 약 8초 — 시안 `undoToast`; 일정 · 할 일 · 리마인더의 되돌리기 로직은 M1-02에서 추가됨).

- 로컬 파서 범위는 **바꾸지 않는다**(설계도 4.2): 금액 "원" 1개, 수입 · 부정 · 계획 · 질문 표현 거부, 날짜 · 동행어가 있으면 AI로 넘김, 금액 2개 이상이면 처리하지 않음. **묶음 표현("총 · 합쳐서 · 다 해서 · 전부 해서 · 모두")이 있으면 로컬에서 처리하지 않고 AI로 넘긴다**(4.5, 시안 `localParse` 보정).
- 시험: 설계도 14.6의 "커피 안 샀어 5000원"과 4.2 · 14.5의 거부 범주(부정 · 계획 · 질문 · 수입) 문장은 로컬에서 저장되지 않는다. "살 거야", "얼마야?"는 설계도에 없는 **명세 추가 예시이므로 앱 소유자 승인 후** 시험에 넣는다.

### M1-12 글자 크기 (T5, 설계도 10.2)
- 범위 70~200%, 10% 단위 14단계, 슬라이더 + [−][+] + "130%" 표시 + 미리보기 문장 + [기본값으로] + "시스템 글자 크기 따르기" 스위치(켜면 슬라이더 비활성).
- 구현: 배율 컨텍스트 + `scaleFont` / `scaleSpace` / `scaleIcon` 헬퍼(README 6.4). 기존 스타일 키(`expense-styles.ts`)의 `fontSize`를 직접 쓰는 곳을 모두 헬퍼로 바꾼다 — **여러 화면이 공유하는 파일이므로 바꾸기 전에 영향받는 화면 목록을 먼저 보고한다**(`CLAUDE.md`).
- 설정은 `settings` 테이블(`fontScale`, `followSystemFont`)에 저장. 앱 시작 시 깜빡임 없이 적용.
- 시험(자동): 헬퍼 값(70% → 0.7배, 200% → 간격 1.5배), 터치 영역 최소 44 유지. **시험(실기기):** 70 · 100 · 130 · 200%에서 홈 · 캘린더 · 지출 · 설정 · 보내기 시트 등 모든 화면 확인.
- 완료 기준: 200%에서 모든 화면이 잘림 없이 사용 가능, 가로 스크롤 없음.

### M1-13 엑셀 내보내기 (T6, 설계도 10.3, 시안 `#exportSheet`)
- 라이브러리 선택(프론트 구현 시 결정, 사유를 보고): SheetJS 계열 또는 exceljs + `expo-file-system` + `expo-sharing`. `npx expo install`로 설치.
- 형식 `.xlsx`, 시트 2개 "지출" · "일정". 선택: 기간(전체 / 이번 달 / 직접 선택), 종류(지출 / 일정 / 둘 다). 파일명 `VoiceLife_YYYY-MM-DD.xlsx`.
- 지출 열: 날짜, 시간, 구분(지출/수입), 금액(숫자 서식 `#,##0`), 카테고리, 메모, 입력 방식(직접/텍스트/음성), 출처("내가 입력" / "OO님이 입력" — M1에서는 항상 "내가 입력"), 합계 포함(예/아니오).
- 일정 열: 시작 날짜, 시작 시간(대략적이면 그 표현, 종일이면 "종일"), 종료, 제목, 장소, 상태(예정/지남/완료/취소), 알림(분 전 목록), 출처, 공개(공개/비공개), 수정됨(예/아니오).
- 삭제한 항목 제외, 시간은 기기 시간대. **수식 주입 방지:** 모든 텍스트 셀을 문자열 형식으로 강제(`=`, `+`, `-`, `@`로 시작해도 수식으로 실행되지 않음). 게스트도 가능, 서버 사용 없음.
- 실패(용량 · 권한): 오류 문구 + "기간을 줄여서 다시 시도해 주세요" + [기간을 이번 달로 줄이기] 버튼. 완료 화면을 띄우지 않는다(15).
- 시험(자동): `=1+1`, `+SUM(A1)`, `-2`, `@x`로 시작하는 메모가 문자열로 들어감, 열 순서, 삭제 항목 제외, 기간 필터, 빈 기간(건수 0이면 만들기 비활성). **실기기:** 공유 시트로 저장 · 전송, 한글이 깨지지 않음.

### M1-14 설정(T1) 로컬 부분 (설계도 10.1, 시안 `#settingsPage`)
- 섹션: 알림(전체 · 나 · 기본 알림 · 잠금 화면 제목 표시 · 권한 상태 · [설정 열기]), 화면(글자 크기), 내 데이터(엑셀, 초기화 (c) — 게스트는 폰 데이터만 지움, 2단계 확인), 정보(이용약관 · 개인정보 처리방침 링크 · 문의하기 · 오픈소스 라이선스 · 앱 버전).
- 로그인이 필요한 섹션(내 프로필 · 구독 · 공개 범위 · 보내기 · 친구 · 계정)은 M2 이후. 게스트 화면에 로그인 안내 한 줄.
- 초기화 (c)와 같은 위험 동작은 빨간색 버튼 + 2단계 확인(단어 입력 또는 길게 누르기, 3.7 · 11.3).
- 설정 화면이 알림 우선순위에 쓰는 값(`allOn`, `ownOn`, `ownDefault`, `lockscreenShowTitle`)은 `settings` 테이블에 저장하고 M2에서 백업 대상이 된다.

### M1-15 지출 화면 보강 (E1 · E2, 기존 `features/money`)
- 월 합계(받은 지출 포함 여부 반영은 M4), 카테고리별 합계, 목록. `include_in_total`이 false인 지출은 합계에서 제외하되 목록에는 보임("합계에서 제외" 표시).
- 묶음 지출(`bundle_items`)은 메모와 별개로 보존(선택, 설계도 12.3) — M3에서 채워짐. M1에서는 컬럼만.

### M1-16 접근성 · 200% 점검
- 모든 버튼에 접근성 이름, 선택 상태 · 비활성 상태는 `accessibilityState`로 전달(12.6). 색만으로 상태를 구분하지 않음.
- 실기기 VoiceOver / TalkBack으로 홈 → 일정 입력 → 캘린더 → 알림 설정 흐름을 한 번 훑는다. 읽기 순서와 이름 문제를 목록으로 보고.
- 70 · 100 · 130 · 200% 각각에서 화면별 캡처를 남겨 비교한다.
